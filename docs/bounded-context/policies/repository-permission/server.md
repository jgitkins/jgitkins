# Repository READ/WRITE 권한 명세 (Server)

## 1. 목적
- 서버를 최종 보안 경계로 두고, 쓰기 API를 권한 기반으로 강제 차단한다.
- Web UI 제어 여부와 무관하게 동일한 권한 정책을 일관되게 집행한다.

## 2. 가시성과 권한 규칙

### 2.1 가시성 (VISIBILITY)
응답 코드를 가르는 기준이므로 권한보다 먼저 정의한다.

- Public 저장소: 모두에게 가시 (비로그인 포함)
- Private 저장소: Owner / Org Member(역할 무관) / Repo Member 에게만 가시
- **멤버 목록은 저장소 가시성과 별개다.** 저장소를 볼 수 있어도 멤버 목록은
  저장소 소유자에게만 가시인 관리 메타데이터다. Public 저장소라도 마찬가지다.

가시성 판정은 `GitRepositoryAccessService.resolvePermission(Repository, Long)` 한 곳에만 둔다.
같은 규칙을 두 벌 두면 갈라지고, 갈라진 쪽이 나중 변경이 잊은 쪽이 된다.

### 2.2 권한
- `READ` — 가시성과 동일
- `WRITE` — Owner / Org Member(MEMBER 제외) / Repo Member(WRITER·MAINTAINER)
- `MANAGE_MEMBER` — 멤버 추가/제거/조회
  - USER 소유: 소유자 본인만
  - ORGANIZATION 소유: 조직의 `OWNER` 만
- `DELETE` — 저장소 삭제
  - USER 소유: 소유자 본인만
  - ORGANIZATION 소유: 조직의 `OWNER` 만

`DELETE` 는 `MANAGE_MEMBER` 보다 큰 권한이므로 멤버 관리가 막는 역할에게 열 수 없다.
조직 `MAINTAINER` 는 push 할 수 있지만 저장소를 지울 수 없다 — 의도된 모양이다.

## 3. 적용 범위
쓰기 API
- 브랜치 생성 API
- 파일 생성(커밋) API
- 디렉터리 생성(커밋) API

관리 API
- **저장소 삭제 API** (`DELETE /api/repositories/{repositoryId}`)
- **저장소 멤버 추가/제거/조회 API**

## 4. 응답 규약
거부는 **연산이 아니라 가시성**으로 나눈다.

| 상황 | 응답 |
|---|---|
| 요청자가 볼 수 없는 리소스 | `404 Not Found` |
| 볼 수 있으나 해당 조작 권한 없음 | `403 Forbidden` |
| 인증 누락/만료 (가시 리소스에 한함) | `401 Unauthorized` |

- 비공개 저장소에 `403` 을 주면 상태 코드만으로 그 id 가 실재함을 알린다. 그래서 `404` 다.
- 공개 저장소에 `404` 를 주면 요청자가 눈으로 읽을 수 있는 리소스를 없다고 말하는 셈이다.
  막으려던 것보다 나쁜 거짓말이므로 `403` 이다.
- 비공개 저장소에 대한 비로그인 요청은 `401` 이 아니라 `404` 다. `401` 도 실재를 알린다.
- 멤버 관리는 §2.1 에 따라 모든 거부가 가시성 거부이므로 **전부 `404`** 다. 이는 위 표의
  예외가 아니라 적용 결과다.
- 응답 본문은 공통 에러 스키마(`code`, `message`, `requestId`)를 사용한다.
  `404` 를 주면서 "삭제 권한이 없습니다" 라고 쓰면 누출이 되돌아온다. 메시지도 함께 맞춘다.

## 5. 헥사고날 아키텍처 기준
- 권한 판단 규칙은 애플리케이션 계층 유스케이스에 위치
- 컨트롤러/어댑터는 인증 주체 전달과 예외 매핑만 수행
- 인프라 어댑터(DB/외부 API)는 멤버십/소유 관계 조회를 책임

## 6. 대안 비교
- 대안 A: 컨트롤러에서 직접 권한 체크
- 장점: 단순
- 단점: 유스케이스 재사용성/테스트성 저하
- 대안 B: 도메인 서비스에서 전부 처리
- 장점: 규칙 캡슐화
- 단점: 인증 컨텍스트 결합 시 경계 혼재 가능
- 대안 C: 애플리케이션 유스케이스에서 권한 포트로 판단
- 장점: 헥사고날 경계 적합, 테스트 용이, 어댑터 독립성 유지
- 단점: 포트/DTO 설계 필요

선택: `대안 C`

## 7. 테스트 기준
"정책 일치" 같은 미결 표현을 쓰지 않는다. 미룬 결정은 구현에서 갈린다 — §9 가 그 사례다.

`✅` 는 테스트로 강제되는 행, `⚠️` 는 명세일 뿐 현재 구현이 다른 행이다.
2026-08-28 기준 `⚠️` 행은 없다 — 표 전체가 테스트로 강제된다.
구현되지 않은 행을 구현된 것처럼 적지 않는다 — 그 착각이 §9 의 결함을 만들었다.

| 저장소 | 요청자 | READ | WRITE | DELETE |
|---|---|---|---|---|
| Public | 비로그인 | 200 ✅ | 401 ✅ | 401 ✅ |
| Public | 비멤버 로그인 | 200 ✅ | 403 ✅ | 403 ✅ |
| Private | 비로그인 | 404 ✅ | 401 ✅ | 401 ✅ |
| Private | 비멤버 로그인 | 404 ✅ | 404 ✅ | 404 ✅ |
| Private | Org MEMBER | 200 ✅ | 403 ✅ | 403 ✅ |
| Private | Org MAINTAINER | 200 ✅ | 200 ✅ | 403 ✅ |
| Private | Org OWNER | 200 ✅ | 200 ✅ | 204 ✅ |
| Private | Repo WRITER | 200 ✅ | 200 ✅ | 403 ✅ |
| 임의 | 소유자(USER) | 200 ✅ | 200 ✅ | 204 ✅ |

**비로그인 행이 401 인 것은 예외가 아니다.** 쓰기·삭제는 저장소를 조회하기도 전에 인증을
요구하므로, 존재하든 안 하든 **모든 id 에 똑같이 401** 이 나간다. 차등이 없으니 존재 신호도
없다. 읽기만 익명을 허용하므로 읽기에서만 404 로 갈린다.

**`Public` + `비멤버 로그인` + `READ` 가 200 인 것은 2026-08-28 에 고쳐진 것이다.**
그 전에는 403 이었다 — 로그아웃하면 보이고 로그인하면 안 보였다. §11 참조.

가드가 공허하지 않음을 변이로 증명한다. 권한 분기를 무조건 허용으로 바꿨을 때 해당
테스트가 실제로 실패해야 하며, 실패하지 않으면 그 테스트는 아무것도 지키지 않는다.

## 8. 후속 개선안 3가지
- 권한 판정 결과 캐시(짧은 TTL)로 API 지연 최소화
- 정책 변경 추적을 위한 감사 로그 확장
- 권한 정책 버전 필드 도입으로 클라이언트/서버 호환성 관리

이번 반영 선택: 감사 로그 확장을 우선 반영 후보로 지정


## 9. 이 명세가 비어 있어서 생긴 결함 (2026-08-28)

3절에 삭제 API 가 없었고 2절에 `DELETE` 권한이 없었다. 그 결과
`RepositoryValidator.enforceDeletionPermission` 이 `ownerType != USER` 이면 아무 검사 없이
반환했고, 그것이 삭제 경로의 유일한 권한 검사였다. 인증만 된 사용자가 임의 조직의 저장소를
DB·git 째로 삭제할 수 있었고 되돌릴 수 없었다.

테스트가 없었던 것이 아니라 `deleteRepository_deletesWhenAccessible` 이 그 삭제의 성공을
단언하고 있었다. 결함이 정상 동작으로 명세화돼 있었다.

**명세에 없는 규칙은 구현되지 않고, 구현되지 않은 규칙은 테스트가 지켜준다고 착각된다.**
그래서 이 문서는 권한을 추가할 때 §3 적용 범위와 §7 표를 같이 채워야 완료로 본다.

## 10. 읽기·쓰기 경로의 존재 오라클 (2026-08-28 해소)

`RepositoryAccessValidator` 가 읽기·쓰기 거부를 모두 `ACCESS_DENIED`(403)로 냈다. 비공개
저장소를 볼 수 없는 요청자가 403 을 받으므로 상태 코드만으로 그 id 의 실재를 알 수 있었다.
§4 가 삭제 경로에서 막은 것과 같은 누출이었다.

이제 §4 규칙을 그대로 적용한다.

- `validateReadAccess` — 읽기 거부는 정의상 "볼 수 없음" 이므로 **항상 404**. 메시지에 저장소
  이름을 넣지 않는다. 404 를 주면서 본문이 이름을 말하면 누출이 되돌아온다.
- `validateCanCommit` — 볼 수 없으면 404, 볼 수 있는데 못 쓰면 403. 가시성 조회는 **거부
  분기에서만** 실행되므로 허용 경로는 비용을 치르지 않는다.

`canRead` 는 저장소가 아예 해석되지 않을 때도 false 다. 없는 이름과 못 보는 이름이 같은 답을
받는 것은 의도된 것이다.

## 11. 로그인하면 공개 저장소를 못 읽던 결함 (2026-08-28 해소)

§10 을 손대려고 `RepositoryAccessValidator` 를 열었다가 발견했다. 같은 메서드의 더 큰 결함이다.

`GitRepositoryAccessService.decide` 의 공개 저장소 지름길은 `isPublic && userId == null` 이다 —
**익명만** 커버한다. 인증된 비멤버는 그대로 떨어져 `none()` 이 되고 `member()` 가 false 다.
`validateReadAccess` 가 `member()` 만 봤으므로, 공개 저장소를 비로그인으로는 읽고 로그인하면
403 을 받았다.

기존 테스트 `allowsAnonymousReadOfAPublicRepository` 가 못 잡은 이유는 명확하다. 익명은
지름길이 커버하는 **바로 그 한 경우**다.

원인은 규칙이 세 벌로 갈라져 있던 것이다 — 문자열 키의 `canRead`, 애그리거트 키의 삭제 정책,
읽기 모델 키의 접근 검증기. 공개 분기를 빠뜨린 건 검증기 하나뿐이었다.
`RepositoryPermission#visibleOn` 이 규칙을 한 번만 적고 함정도 함께 적는다.

**`member()` 는 "멤버인가" 가 아니다.** 공개 저장소 + 익명에서 true 이고 그 요청자는 멤버가
아니다. 뜻은 "읽을 수 있는가" 인데, 그것도 PUBLIC 을 먼저 본 뒤에만 그렇다.
